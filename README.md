# Кейс 5. Entity Resolution для compliance-платформы ClearPic

Дедупликация и поиск записей о физических и юридических лицах в базе
на 6 стран и 3 алфавита (3,73 млн записей). Инференс на CPU, упаковано
в Docker, REST API с Swagger.

Автор: Горохов Артём. Проектный практикум МФТИ, 2026.

## Главные выводы

1. **Gold-разметка (`party_public_id`) непригодна для обучения.** Она есть
   у 3% записей, но в 100% кластеров имя записано побайтово одинаково -
   это одна запись из разных снапшотов, а не варианты написания. Модель,
   обученная на ней, выучит правило «строки равны -> дубль» и покажет
   F1 ≈ 0,99, ничего не найдя на реальных расхождениях.
2. **Cross-country дубли не размечены вообще.** Surrogate key строится
   внутри страны, поэтому ноль идентификаторов пересекают границу.
   Самая сложная часть задачи в разметке отсутствует как класс.
3. **Обучающий набор построен синтетически:** позитивы - 8 типов
   реалистичных искажений имени, негативы - однофамильцы (та же фамилия,
   другое имя) плюс случайные пары.
4. **Плейсхолдеры ломают кластеризацию:** имена вида «неизвестная
   организация» стоят у тысяч компаний; без стоп-листа один кластер
   вырастает до 50 737 записей. Правило: имя у ≥ 50 разных компаний или
   короче 3 символов не резолвится (247 имён, 3,3% базы). Крупнейший
   кластер после этого 14 521. Подробности выбора порога в разделе
   «Ограничения».
5. **Cross-country по одному имени не решается:** нечёткий матчинг
   находит 19 906 кластеров против 3 875 контрольных -
   однофамильцев между странами больше, чем совпадений. Нужен контекст
   (общие компании, роли, даты). Это главная точка роста.

## Запуск

```bash
pip install -r requirements.txt
```

Указать путь к датасету в `config.py` (переменная `DATA`) или через
`ER_DATA=...`. Затем по порядку:

```bash
python 01_eda.py "$ER_DATA" --gold party_public_id   # EDA, графики в eda_out/
python 01c_crosscountry.py                            # cross-country проверка
python 04_quality_report.py                           # обучение, отчёт, тестовый набор
python 03_dedup.py                                    # дедупликация всей базы (~5 мин)
```

Ноутбуки запускаются в JupyterLab и уже содержат выводы.

## API

```bash
uvicorn api.app:app --port 8000
# Swagger: http://localhost:8000/docs
```

Docker:

```bash
docker compose up --build
```

| Метод | Что делает |
|---|---|
| `POST /check_duplicate` | вероятность того, что две записи - одна сущность |
| `POST /search` | top-K похожих записей из базы (нужен индекс: `ER_INDEX=путь.parquet`) |
| `POST /deduplicate_batch` | кластеры для батча записей |
| `GET /health` | готовность сервиса |

Пример:

```bash
curl -X POST localhost:8000/check_duplicate \
  -H "Content-Type: application/json" \
  -d '{"left":"Ғабдуллин Қанат","right":"Gabdullin Kanat"}'
# {"probability": 1.0, "is_duplicate": true, ...}
```

## Ограничения

- Cross-country матчинг по одному имени переклеивает; нужны контекстные признаки.
- Стоп-лист: порог 50 компаний выбран по кривой чувствительности (покрытие
  4,6% при 20, 3,3% при 50, 3,0% при 100); ниже 30 под отсечение попадают
  ФИО с 20-40 компаниями. Правило по частоте строк вместо компаний отсекало
  бы 83% Армении (там 40 снапшотов на человека). Среди отсечённых 101 имя
  помечено `individual`; в продакшене их правильнее отправлять на ручную
  проверку, а не отсекать.
- Кластеризация - транзитивное замыкание; одна ошибочная связь склеивает кластеры.
- Компании проработаны слабее физлиц: у них названия типовые, точность ниже.
- Задача «party - company» не реализована.
- Модель обучена на синтетических искажениях; соответствие реальным проверено косвенно.
